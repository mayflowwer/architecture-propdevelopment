# Требования к безопасности PropDevelopment

## 1. Общие положения

### 1.1 Область применения
Настоящие требования применяются ко всем контрагентам PropDevelopment, осуществляющим обмен данными через API, включая:
- Передачу биометрических данных собственников жилья
   другие операции, требующие защищенного соединения

### 1.2 Юридическая основа
Для начала работы с PropDevelopment контрагент обязан:
1. Заключить договор с PropDevelopment на оказание услуг, в т.ч. обработки персональных данных клиентов PropDevelopment
2. Договор обязан содержать : 
   - правила обработки персональных данных собственников
   - Меры защиты информации
   - Ответственность контрагента за нарушения
   - Процедуры уведомления об инцидентах информационной безопасности

---

## 2. Аутентификация контрагента
Осуществляется через через Mutual TLS (mTLS).

### 2.1 Использование клиентских сертификатов

#### 2.1.1 Получение сертификата
Контрагент обязан получить клиентский сертификат, выданный Certificate Authority (CA) PropDevelopment:

1. Контрагент генерирует пару ключей (приватный и публичный) и создает запрос на подпись сертификата (CSR — Certificate Signing Request)
2. Контрагент передает CSR представителю PropDevelopment защищенным способом (email с PGP, защищенный портал, лично)
3. PropDevelopment проверяет личность контрагента и правомочность запроса
4. PropDevelopment подписывает CSR своим CA и выдает клиентский сертификат контрагенту
5. PropDevelopment регистрирует fingerprint сертификата в системе авторизации

**ВАЖНО:** Приватный ключ генерируется контрагентом и НИКОГДА не передается PropDevelopment.

#### 2.1.2 Срок действия сертификата
- Клиентский сертификат действителен в течение **1 года** с момента выдачи
- За **30 дней** до истечения срока действия PropDevelopment уведомляет контрагента о необходимости обновления сертификата
- Контрагент обязан инициировать процесс обновления сертификата не позднее чем за **14 дней** до истечения срока действия текущего сертификата

#### 2.1.3 Обновление сертификата
При обновлении сертификата:
1. Контрагент генерирует новую пару ключей и создает новый CSR
2. PropDevelopment выдает новый сертификат
3. В течение **7 дней** оба сертификата (старый и новый) остаются действительными
4. По истечении grace period старый сертификат автоматически отзывается

---

### 2.2 Защита приватного ключа

#### 2.2.1 Требования к хранению
Контрагент обязан:
- Хранить приватный ключ в защищенном хранилище с шифрованием
- Ограничить доступ к приватному ключу минимальным числом лиц (принцип наименьших привилегий)
- Использовать парольную защиту приватного ключа (минимум 16 символов)
- **Рекомендуется:** Использовать Hardware Security Module (HSM) или аналогичное защищенное устройство для хранения приватного ключа

#### 2.2.2 Компрометация ключа
В случае компрометации или подозрения на компрометацию приватного ключа контрагент обязан:
1. Немедленно (в течение **2 часов**) уведомить PropDevelopment
2. Прекратить использование скомпрометированного ключа
3. Запросить отзыв сертификата

PropDevelopment обязуется:
1. Немедленно отозвать скомпрометированный сертификат
2. Выдать новый сертификат в течение **24 часов** с момента получения уведомления и нового CSR

---

## 3. Транспортная безопасность

### 3.1 Протокол TLS

#### 3.1.1 Требования к версии TLS
Все коммуникации между контрагентом и API PropDevelopment ОБЯЗАТЕЛЬНО осуществляются через:
- **TLS 1.3** (рекомендуется)
- **TLS 1.2** (минимально допустимая версия)


### 3.2 Mutual TLS (mTLS)

#### 3.2.1 Автоматическая аутентификация
При использовании mTLS:
- Аутентификация контрагента происходит **автоматически** на уровне TLS handshake
- **НЕ требуется** дополнительная передача токенов, API ключей или паролей в HTTP заголовках
- **НЕ требуется** подписание каждого сообщения приватным ключом (это уже происходит на уровне TLS)
- Идентификация контрагента происходит по fingerprint клиентского сертификата

---

## 4. Шифрование данных

### 4.1 Шифрование при передаче (Encryption in Transit)
Все данные, передаваемые между контрагентом и PropDevelopment, автоматически шифруются на транспортном уровне через TLS с использованием алгоритмов:
- **Шифрование:** AES-256-GCM или ChaCha20-Poly1305
- **Аутентификация:** Authenticated Encryption with Associated Data (AEAD)

### 4.2 Шифрование биометрических данных (дополнительное)

#### 4.2.1 Биометрические шаблоны
При передаче биометрических данных контрагент ОБЯЗАН:
1. **НЕ передавать** сырые биометрические данные (фотографии лиц, отпечатки пальцев в оригинальном виде)
2. **Передавать** только биометрические шаблоны (feature vectors) — математические представления биометрии, из которых невозможно восстановить оригинальное изображение
3. Биометрические шаблоны генерируются с использованием признанных алгоритмов (FaceNet, ArcFace, или аналогичных)
